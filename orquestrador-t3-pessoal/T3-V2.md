# Orchestrator V2 · o que o orquestrador usa

O servidor do T3 0.1.0 fala o **protocolo de orquestração 2** (`/.well-known/t3/environment`). A API HTTP do
protocolo 1 (`/api/orchestration/snapshot` e `dispatch`), que o antigo `t3ctl` usava, não existe mais. Toda a
coordenação passa pelas ferramentas MCP `t3-code` desta thread. Os nomes podem vir com prefixo
(`mcp__t3-code__delegate_task`); a semântica é a mesma.

## Mapa

| Preciso de… | Ferramenta V2 | Observações |
|---|---|---|
| Saber modelos, provedores e opções disponíveis | `orchestrator_capabilities` | Mesmo catálogo do compositor. Confira `canRunChildTask` do provedor antes de usá-lo |
| Criar o implementador ou o revisor de uma tarefa | `delegate_task` | `mode:"async"`, `isolation:"worktree"`, `role`, `title`, `target` (de `bin/alvo.py --tarefa <ID>`, sempre com o effort declarado), `clientRequestId` estável |
| Saber se um agente terminou, está trabalhando ou esperando subagentes | `task_status` | `workState`: `working`, `waiting_for_children`, `result_available`. Ler um resultado terminal confirma a entrega |
| Ler a conversa ou as atividades de um agente | `t3_thread_read` (`threadId` = `childThreadId`) | `view:"activity"` mostra ferramentas e subagentes; pagine com `afterPosition` |
| Mandar devolutiva, pedido de rebase ou retomada ao mesmo agente | `t3_thread_send` ao `childThreadId` | Se a tarefa original já terminou, cria uma **nova tarefa** no mesmo filho e devolve um `taskId` novo; a conclusão também te acorda |
| Corrigir o rumo de um agente que está rodando | `t3_thread_send` com `mode:"steer"` | Chega no turno em andamento. É assim que a pausa suave começa |
| Parar um agente agora | `task_cancel` | Interrompe o turno, segura a fila, encerra vigílias e para os subagentes dele. O worktree fica intacto |
| Interromper um turno de qualquer thread | `t3_thread_interrupt` | Para threads de topo; para tarefas delegadas prefira `task_cancel` |
| Ver ou limpar mensagens enfileiradas | `t3_queue_list`, `t3_queue_cancel` | Antes de pausar, cancele o que ainda não começou |
| Trocar o modelo ou o effort de um agente antes da próxima mensagem | `t3_thread_configure` (`threadId` = `childThreadId`, seleção de `alvo.py <alvo> --selecao`) | Usado no escalonamento entre ciclos ([`MODELOS.md`](MODELOS.md)). A instrução do modelo novo vai na mensagem seguinte, não numa edição do que já foi enviado |
| Ser acordado por CI, comentário ou conflito de um PR | `watch_pull_request` / `unwatch_pull_request` | Só a thread do orquestrador vigia: um subagente não pode. O T3 confere a cada 2 min |
| Despertar periódico que sobrevive a reinício | `schedule_task` (`{"type":"interval","everyMs":…}`), `update_scheduled_task`, `list_scheduled_tasks`, `delete_scheduled_task` | Fica no agendador do app, ligado a esta thread. Substitui o `/loop` + `ScheduleWakeup` |
| Fixar, assentar ou adiar threads | `t3_thread_organize` (`pin`, `settle`, `unsettle`, `snooze`, `unarchive`) | **Thread fixada nunca é assentada automaticamente**: a do orquestrador fica fixada |
| Mover a thread da montagem para uma worktree própria | `t3_worktree_handoff` | Última ação do turno; use `continuationPrompt` para seguir |
| Listar threads e worktrees | `t3_thread_list` (`includeSubagents:true`), `t3_worktree_list`, `t3_worktree_status` | |
| Responder pergunta pendente de um agente | `t3_pending_request_list`, `t3_pending_request_read`, `t3_pending_request_respond` | Use quando `task_status` indicar `hasPendingQuestion` |

## Regras que o V2 impõe

- **A worktree de uma tarefa delegada nasce do commit local desta thread.** Por isso o orquestrador roda numa
  worktree própria (`CHECKOUT`) que acompanha `origin/$BASE` só com fast-forward. Antes de cada despacho:
  `git -C "$CHECKOUT" fetch origin --quiet && git -C "$CHECKOUT" merge --ff-only "origin/$BASE"`. Edições sem commit
  não são copiadas.
- **O T3 roda o script de setup do projeto** na worktree nova antes de o agente começar. É pesado (instalação de
  dependências): por isso o despacho é escalonado ([`PLAYBOOK.md`](PLAYBOOK.md), passo 5).
- **Cada rodada de revisão é um `delegate_task` novo**, com `clientRequestId` próprio e o histórico no prompt
  (brief, achados anteriores, respostas, objeções em aberto). O `childThreadId` de um revisor não recebe a rodada
  seguinte.
- **`clientRequestId` estável por rodada** (`<ORQ_ID>-<ID>-impl`, `<ORQ_ID>-<ID>-rev-c<N>`): se a resposta se perder,
  repetir a chamada não cria um agente duplicado.
- **Conclusões chegam sozinhas.** Termine o turno em vez de esperar em laço. Use `task_status` só quando precisar do
  resultado no meio de um turno, ou na varredura.
- **`runtimeMode` fica herdado.** Modos com aprovação fazem o agente esperar uma pessoa a cada ação.
- **Limite de uso:** o V2 registra o horário de reset (`limitRecovery`). Com "Auto-resume limited threads" ligado
  nas configurações do T3, as threads limitadas continuam sozinhas no reset.

## Perguntas ao usuário: o painel do `AskUserQuestion`

O T3 intercepta o `AskUserQuestion` do Claude e abre um pedido de resposta (`user_input`) no lugar do compositor.
Conferido no código do servidor e da interface do T3 0.1:

- **Uma pergunta por vez:** etiqueta (`header`), texto da pergunta em Markdown, alternativas clicáveis com
  `label` e `description`. Botões **Previous**, **Next question** e, na última, **Submit answers**. Com
  `multiSelect`, a interface avisa que dá para marcar várias.
- **Resposta livre:** o compositor vira o campo "Type your own answer, or leave this blank to use the selected
  option". O texto escrito vence a alternativa marcada.
- **O que chega de volta:** um mapa pergunta → resposta. As escolhas múltiplas vêm unidas por `, `. A chave é o
  texto da pergunta, então duas perguntas iguais na mesma chamada se sobrepõem.
- **O que se perde:** o campo `preview` não passa para a interface. Use só `header`, `question`, `options` e
  `multiSelect`.
- **Fechar o painel** devolve a chamada como cancelada.
- **O painel segura o turno:** enquanto ele estiver aberto, a thread não processa despertares (conclusões,
  heartbeat, vigília de PR). Por isso o painel serve à montagem e ao ensaio, com o usuário presente. No loop, o
  pedido de decisão vai em texto ([`PLAYBOOK.md`](PLAYBOOK.md)).

O formato de cada pergunta está em [`sabatina/SABATINA.md`](sabatina/SABATINA.md); `bin/texto.py --tipo pergunta`
confere o JSON antes da chamada.

## Interface do T3

O que o usuário vê é a thread do orquestrador, a barra lateral e os painéis do T3. Use cada recurso para o que ele
faz melhor; texto corrido é o último recurso.

| Para | Use | Não use |
|---|---|---|
| Perguntar com o usuário presente (montagem, sabatina, ensaio, aprovações) | `AskUserQuestion` (painel acima) | lista de perguntas em texto |
| Pedir decisão no loop | texto no modelo de [`escrita/ESCRITA.md`](escrita/ESCRITA.md), título com `⛔` e `t3_thread_organize` `mark_unread` | o painel: ele segura o turno |
| Citar um agente | link `[🔨 T2.2](t3-thread://v1/<childThreadId>)`: abre a thread do agente com um clique | id solto ou "8 primeiros caracteres" na conversa |
| Mostrar uma prova visual | `![legenda](/caminho/absoluto.png)` ou `.mp4` na mensagem, no máximo 2 | só o caminho do arquivo |
| Mostrar tabela grande, dependências entre tarefas ou o painel | página com `html_preview` e depois `html_render` (backlog, gate, final, `status`) | tabela de 20 linhas em Markdown |
| Mostrar o estado de longe | título da thread (`t3_thread_update` `rename`): `🎛️ <nome> · 🔨 4 rodando`, `· ⛔ 1 decisão`, `· ⏸️ pausado`, `· ✅ concluído`. Troque só quando o estado mudar | mensagem a cada heartbeat |
| Devolver a thread ao usuário (pausa, fim) | `unwatch_pull_request` dos PRs vigiados e `list_thread_pull_requests` para conferir que nenhum PR ficou sem vínculo | deixar vigílias ativas sem ninguém processar |
| Segredo (senha ou token da conta de teste) | terminal do usuário (`secret-tool`, `hml guardar`), com a confirmação pelo painel | `request_secret`: o `secretRef` só serve às ferramentas do T3 (assinatura de webhook), não aos scripts; nunca no chat |

**Agentes não falam com o usuário.** Implementador e revisor não usam `AskUserQuestion` nem pedem nada a ninguém:
a dúvida vai para o relatório ou para `BLOQUEADO`. Se um painel aparecer numa thread de agente, o `task_status`
mostra `hasPendingQuestion`, e o orquestrador responde com `t3_pending_request_respond` (passo 3 do playbook).

## Formato da conclusão dos agentes

Os briefs pedem que a mensagem final comece por um bloco que o orquestrador lê no `summary` do `task_status`:

```text
STATUS: PRONTO | BLOQUEADO | PAUSADO | REVISADO
TAREFA: <ID>
PR: <url ou —>
HEAD: <sha>
WORKTREE: <caminho da worktree do agente>
VEREDITO: APROVAR | MUDANÇAS   (só revisor)
ESCOPO: DENTRO | EXTRAPOLA      (só revisor)
PROVAS: PROVADO | INCOMPLETO    (só revisor)
ARQUIVO: <relatorio.md ou revisao-cN.md>
RESUMO: <uma linha>
```

Sem esse bloco, leia a última mensagem com `t3_thread_read` e os arquivos da tarefa antes de decidir.
